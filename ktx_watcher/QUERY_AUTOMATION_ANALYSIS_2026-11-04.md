# 코레일 조회 -8002 분석과 CDP·UIA·Claude Code 연동 현황

작성 기준: 2026-11-04, Asia/Seoul. 이 문서는 당일 실험과 현재 소스 확인 결과를 기록한다.
실사이트 실험은 조회만 수행했으며 예약·결제는 실행하지 않았다.

## 1. 현재 결론

- **CDP로도 개별 실행 시험에서 정상 조회됐다.** CDP 자체나 모든 CDP 클릭이 차단된다는 결론은 아니다.
- 기존 전체 조회 흐름에서는 첫 제출에 `-8002`가 반복됐다. 마지막 제출만 Windows UIA Invoke로
  바꾸면 첫 조회부터 성공했다. 실패를 가르는 구간은 현재 흐름의 최종 제출 경로로 좁혀졌다.
- **전체 자동화를 단계별로 나누면 반복해서 안정적으로 성공하는지는 아직 검증하지 않았다.**
  개별 시험의 성공을 전체 운영의 안정성으로 일반화하지 않는다. UIA 전면 전환을 결정한 상태도 아니다.
- DynaPath가 검사한 정확한 이벤트 속성·순서·서버 내부 판정 규칙은 확인하지 못했다.
- 운영 조회·감시는 현재 CDP를 사용한다. UIA Invoke는 진단 실험에만 적용돼 있다.
- Claude Code 자동 진단은 일부 연결돼 있지만, 일반 조회 실패와 화면 멈춤을 모두 인계하는 구조는 아니다.

## 2. Runtime 도메인과 CDP 최소화 상태

공통 브라우저 진입점 [browser.py](browser.py)는 `rebrowser-playwright`의
`REBROWSER_PATCHES_RUNTIME_FIX_MODE=addBinding`을 강제한다. 프로젝트의 일반 연결 경로는
`Runtime.enable`을 사용하지 않도록 구성돼 있다.

`Runtime.enable`을 생략해도 `Runtime.evaluate`, `Runtime.callFunctionOn` 등 JavaScript 실행 명령과
`Page`, `Network`, 입력 관련 CDP 명령은 필요하다. 따라서 “Runtime 도메인 활성화 안 함”과
“CDP 또는 JavaScript 평가를 전혀 사용하지 않음”은 다르다.

현재 구현은 DOM 정보를 한 번에 읽고, 메인 탭과 연결을 재사용하며, 팝업 핸들러 중복과 불필요한
마우스 이동·hover·글자별 타이핑을 줄이는 방향이다. CDP 사용량을 줄이는 것이 사이트 차단 해제를
보장하는 것은 아니다. 관련 구현은 [dom.py](dom.py), [client.py](korail/client.py)에 있다.

## 3. -8002 응답과 재현 조건

전체 흐름 비교에서는 다음 조회 조건을 유지했다.

| 항목 | 조건 |
|---|---|
| 출발·도착 | 서울 → 부산 |
| 출발일 | 2026-11-07 |
| 조회 시작 / 감시 시간창 | 09:00 / 09:00~13:00 |
| 승객 | 어른 1명, 어린이 1명 |
| 열차·좌석 | KTX, 일반실, 좌석만 |
| 수서/SRT 포함 | 제외 |
| 브라우저 | 동일 Chrome 인스턴스와 프로필 재사용 |

실패한 첫 조회도 `/web_s/...` 보호 경로로 서버에 전송됐다. HTTP 상태는 `200`이지만 응답 본문은
다음과 같았다.

```json
{
  "strResult": "FAIL",
  "errCode": "macro_err1",
  "dynaPathResultCode": "-8002"
}
```

이는 서버가 반환한 명시적 보안 거절 응답이다. 매진이나 목록 파서 오류와 구분해야 한다.
같은 브라우저에서 조회 폼을 다시 열어 제출할 때도 재현됐으므로 “브라우저 최초 1회성”으로
분류할 수 없다. 날짜 선택기는 이미 값이 일치해 생략한 상태에서도 실패했다.

동일 조건으로 결과 페이지를 전체 새로고침한 뒤에는 `SUCC`와 열차 10행을 받았고,
더보기 후 최종 20행을 읽었다. 이는 복구 성공 사례이며 최초 차단 원인이 해결됐다는 뜻은 아니다.
`report.status=ok`나 최종 20행만 보고 첫 제출도 성공했다고 판단하면 안 된다.

## 4. CDP·UIA 비교 결과

| 비교 조건 | 첫 조회 관측 결과 |
|---|---|
| 프로젝트 CDP 연결 없이 UIA로 조회 폼 진입·제출 | 차단 안내 없이 열차 10행 |
| CDP 연결만 유지하고 UIA로 제출 | `SUCC`, 열차 10행 |
| 제목 JavaScript 읽기 또는 locator 입력값 읽기를 개별 추가하고 UIA 제출 | 각 시험 `SUCC` |
| CDP 페이지 이동과 CDP 조회 클릭을 나눠 실행 | `SUCC`, 열차 10행 |
| 프로젝트 폼 준비 과정 후 UIA 제출 | `SUCC`, 열차 10행 |
| 기존 진단 전체 흐름 | 첫 응답 `FAIL / -8002`, 재조회로 복구 |
| 시작 화면 수집 또는 팝업 핸들러를 각각 제외한 전체 흐름 | 여전히 첫 응답 `FAIL / -8002` |
| 전체 흐름의 마지막 제출만 UIA Invoke로 변경 | 첫 응답 `SUCC`, 차단 0건, 최종 20행 |
| 최종 통제 비교: 공통 요소 탐색·추가 대기 후 CDP 제출 | 첫 응답 `FAIL / -8002`, 재조회 후 최종 20행 |
| 최종 통제 비교: 공통 요소 탐색·추가 대기 후 UIA Invoke 제출 | 첫 응답 `SUCC`, 차단 0건, 최종 20행 |

“프로젝트 CDP 연결 없음” 대조에서도 Chrome의 원격 디버깅 실행 옵션은 유지했다.
확장 프로그램 내부의 디버거 연결 여부까지 배제한 실험은 아니다.

최종 통제 비교는 `final-controlled-cdp`와 `final-controlled-uia` 기록이다. 조회 전 스크린샷을
제외하고 화면 크기를 복원했다. 제출 직전 두 시험 모두 내부 크기 `1718×1270`, 외부 크기
`1734×1399`였으며, `document.hasFocus()`, 가시성, 사용자 활성화 값과 전경 창 식별값이 같았다.
실행 시각과 모든 내부 상태까지 완전히 동일한 통계적 반복 실험은 아니다.

중간 `matched-*` 비교에서는 전체 화면 캡처 시간 초과 후 내부 화면 높이가 달라진 사례가 있었다.
따라서 해당 쌍만으로 결론내리지 않고, 화면 크기를 확인한 최종 쌍을 비교 근거로 사용했다.
캡처 시간 초과와 크기 변경의 정확한 인과, 이것이 차단에 미치는 영향은 별도 문제다.

**해석:** 현재 전체 흐름의 마지막 제출 방식에 따라 결과가 갈린다. 하지만 개별 CDP 클릭은
성공했으므로 CDP 클릭을 일괄 금지할 근거는 없다. 입력 이벤트 차이, 앞선 동작과의 조합,
제출 시점 중 구체적으로 무엇을 보안 모듈이 판단했는지는 미확정이다.

## 5. UIA의 의미와 이번 사용 방식

UIA는 Windows UI Automation이다. 접근성 인터페이스를 통해 창·버튼·입력칸을 식별하고
정보를 읽거나 기본 동작을 실행할 수 있다. [Microsoft 설명](https://learn.microsoft.com/en-us/windows/win32/winauto/entry-uiauto-win32)

이번 실험은 다음 방식이었다.

> Chrome의 코레일 문서 → 이름이 ‘열차 조회’인 버튼 찾기 → `InvokePattern.Invoke()` 실행

- **LLM은 필요 없다.** 실행한 PowerShell 코드는 모델 호출 없이 대상 요소를 찾아 실행했다.
- **이 Invoke 방식은 픽셀 좌표가 필요 없다.** 대상 창·페이지·버튼 이름으로 식별한다.
  같은 이름의 요소가 여러 개라면 영역이나 요소 종류까지 구분해야 한다.
- 해당 요소가 접근성 정보와 실행 동작을 제공해야 한다. 사람의 직접 마우스 클릭과 동일한
  방식이라고 가정하지 않는다.
- LLM은 상황을 해석하고 다음 행동을 결정하는 계층에 선택적으로 붙일 수 있다.
  정해진 조회 절차 자체는 일반 코드로 실행할 수 있다.

[win_watch.ps1](win_watch.ps1)은 별도 도구다. UIA로 요소를 확인한 뒤 OS 마우스 좌표 클릭을
수행하므로 이번 Invoke 실험과 구분한다. 웹 서버나 기본 워처가 이 스크립트를 호출하지 않는다.
사이드 패널 확장의 탭 제어 방식은 이번 비교에서 시험하지 않았다.

## 6. 운영 코드와 Claude Code 복구의 현재 범위

| 기능 | 현재 상태 |
|---|---|
| 웹 일반 조회·감시 실행 | `KorailSPAClient`를 통한 CDP 경로 |
| UIA Invoke 조회 제출 | `runs/guard-analysis/`의 진단 실험만 존재, 운영 미통합 |
| Claude Code 실행 환경 | 확인 시점 CLI 설치·로그인 정상 |
| Claude 자동 진단 호출 | 2026-11-03 로그에 실제 호출 기록 있음. 복구 성공을 뜻하지는 않음 |
| 웹에서 시작한 감시 프로세스의 오류 종료 | 종료 감시 조건을 만족하면 Claude 진단 호출 |
| 일반 조회 API의 실패 | 오류 응답 반환, Claude 자동 진단으로 연결되지 않음 |
| 프로세스가 살아 있는 화면 멈춤·일반 예외 반복 | 별도 무응답 감시와 Claude 자동 인계 없음 |
| Claude가 결정할 수 있는 복구 | 모달 닫기, 검색 화면 이동, 최대 2회 워처 재시작 |
| 복구의 브라우저 조작 | `_cdp_ops()`가 CDP 사용 |

[web_server.py](../web_server.py)의 `_start_watcher_proc()`는 `ktx_watcher.main`을 실행하고
`_monitor_proc()`를 붙인다. 종료 코드와 로그를 보고 비정상 종료로 판단할 때
`_ai_recover()` → Claude CLI 호출로 이어진다. 사용자 중지와 정상 종료는 제외한다.

Claude에는 로그 일부와 현재 URL·모달·본문 텍스트를 전달한다. 반환된 JSON에 따라 코드가
허용된 복구 동작을 실행한다. 스크린샷을 첨부해 모든 화면 장애를 분석하거나, 사이트 구조가
바뀔 때 자동으로 코드를 고치는 복구 절차까지 연결된 상태는 아니다.

[main.py](main.py)의 조건 불일치·불완전 목록·화면 구조 오류는 오류 종료로 이어질 수 있다.
일반 예외는 재시도하며 프로세스가 살아 있으면 종료 감시 기반 Claude 복구는 시작되지 않는다.
연속 차단도 설정한 중단 횟수에 도달해 종료해야 이 경로에 들어갈 수 있다.
CLI에서 직접 실행한 워처나 진단 명령에는 웹 서버의 종료 감시가 자동으로 붙지 않는다.

일반 조회의 차단 오류는 내부에서 HTTP 503을 만들지만, 현재 최상위 API의 넓은 예외 처리로
500으로 다시 감싸질 수 있다. 이 상태 코드 문제와 Claude 자동 인계 미구현은 구분해야 한다.

## 7. 후속 검증과 미구현 항목

사용자가 제안한 **CDP 유지·단계별 실행**을 검증 가능한 방향으로 남긴다. 아래 항목은 이번
문서 작성에서 구현하거나 완료한 내용이 아니다.

1. 페이지 이동 → 폼 준비 완료 확인 → 조건 설정 → 조건 재확인 → 제출 → 응답·화면 확인으로
   실행 단계를 나눈다. 단순 고정 대기 추가와 구분한다.
2. 같은 조건에서 전체 단계별 흐름을 반복 검증한다. 각 단계의 시작·완료 상태와 첫 응답,
   차단 횟수, 복구 여부를 따로 기록한다.
3. 필요하면 마지막 제출 방식의 대안으로 UIA Invoke를 비교한다. 조회 성공을 예약·결제까지의
   안정성으로 확대 해석하지 않는다.
4. 일반 조회 실패·화면 멈춤을 감지해 진단 자료를 남기고 Claude로 인계하는 연결 지점을 설계한다.
   기존 감시 종료 복구와 중복 실행되지 않게 해야 한다.
5. “UIA 조회 + 장애 감지 + Claude 복구”를 하나의 운영 경로로 연결할지는 이후 결정한다.

## 8. 근거와 정정 사항

다음 표현은 이번 증거와 맞지 않아 사용하지 않는다.

- “-8002는 날짜 선택기를 반복 클릭해서 발생한다.” → 날짜 선택기를 생략해도 재현됐다.
- “브라우저 최초 조회에서 한 번만 발생한다.” → 같은 브라우저에서 새 폼 제출 시 반복됐다.
- “조회 XHR가 서버로 나가지 않는다.” → 보호 경로 요청과 `FAIL` 응답을 확보했다.
- “CDP를 쓰면 조회가 불가능하다.” → 개별 CDP 이동·클릭 시험은 성공했다.
- “UIA면 문제없다” 또는 “단계별 CDP 자동화는 이미 안정적이다.” → 검증 범위를 넘는 결론이다.
